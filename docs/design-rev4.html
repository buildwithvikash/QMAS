01Understanding of the project

QMAS IMI & DN digitises the Incoming Quality Control (IQC) lifecycle for purchased material across the plants: from the moment an inward lot is posted in SAP (inspection lot under QA32) to the final usage decision on that lot, including deviation handling with Supply Chain (SCM) / Vendor Development (VD), a seniority-based escalation matrix, and a supplier Defect Notification (DN) with CAPA closure.

Phase 1 Format creation

Every item code needs an approved inspection format (the "JIR" — Product Inspection Test Standard cum Joint Inspection Report) with Dimensional, Visual and Reliability checkpoints. Source: pre-fed migration, SAN/SIR fetch, or built new. IQC Head approves; every revision is versioned.

Phase 2 Physical inspection

Lot fetched from SAP opens an IMIR (number generated, status OPEN). Sampling per IS 2500 S1 / AQL 2.5 decides which sample boxes are mandatory. Inspector records observations; dimensional and visual results are auto-judged; reliability is manual. Submission locks data.

Phase 3 Review & closure

IQC Incharge approves, reverts or escalates. IQC Head approves or puts on hold with deviation types (UAI / Segregation / Rework). SCM/VD raise a deviation, their head reviews, IQC Head accepts or escalates to senior authority. Quantity verification, 14-day auto-closure, and DN/CAPA run alongside.

02Proposed application architecture

A modular monolith: one Node.js service with strict module boundaries (formats, IMIR, deviation, escalation, DN, masters, integration), one PostgreSQL database, and a background worker process running from the same codebase. It keeps the WRL Tool Report code shape (Express API, React build) while fixing the parts that don't scale well there, and runs on AWS managed services so the team does not operate servers or database replicas. Microservices would add operational cost with no benefit at this user volume.

Backend layering (keeps WRL's folder names, adds two layers)

backend/src/
  config/          env schema (zod), db pool, mail, logger
  middlewares/     authenticate, authorize(permission), plantScope, validate(schema), errorHandler, requestId
  modules/
    imir/          imir.routes.js  imir.controller.js  imir.service.js  imir.repo.js  imir.schema.js  imir.policy.js
    format/  deviation/  escalation/  dn/  masters/  users/  reports/  notifications/
    integration-sap/   integration-san/   offline-sync/   numbering/
  workflow/        state machines (IMIR, Format, Deviation, DN) — transitions, guards, side-effects
  jobs/            sap-sync, escalation-tat, qty-auto-close, capa-reminder, mail-outbox
  db/migrations/   versioned SQL (node-pg-migrate)
  shared/          AppError, tryCatch, pagination, docNumber, audit, fileStore
server.js · worker.js
  • Controllers only parse the request and shape the response. Services own business rules and open the transaction. Repositories hold parameterised SQL. Policies answer "may this user act on this record" (role + plant + current stage).
  • Workflow engine: each document type has a declarative transition table {from, action, to, roles, guard, effects}. One endpoint executes any action; the engine validates, writes the new state and a history row in the same transaction, then queues notifications. No status changes happen outside it.
  • Concurrency: every workflow table carries row_version; a stale update returns 409 Conflict (two heads acting on one IMIR at once).
  • Integration adapters (SAP, SAN/SIR) sit behind interfaces with timeouts, retries and a circuit breaker, and have a mock implementation so development and tests don't need the real systems.

Format versioning: the Git model (Decision 2)

  • Stable identity: every checkpoint has a checkpoint_uid that survives across versions, so changes are compared per checkpoint and per field (spec, limits, instrument, UOM, frequency, sequence), not by row position.
  • Branch: a draft records base_version_id. Any number of drafts may exist; opening one shows "also being edited by name" as a warning, not a lock.
  • Fast-forward: if the draft's base is still the current approved version, approval simply creates the next version.
  • Three-way merge: otherwise the server compares base ↔ current approved ↔ draft. Changes to different checkpoints or different fields merge automatically. The same field changed to different values, or an edit against a delete, is a conflict.
  • Resolve: conflicts block approval. The draft owner or IQC Head chooses "keep approved", "keep draft" or types a new value; the draft is then based on the new version and goes back into the queue.
  • Queue order: by submission timestamp (Cases 3–4). The IQC Head may still reject any draft.
  • History: every version keeps its parent, author, approver and a stored diff, so any two versions can be compared.

Parallel senior decisions: resolving the effective decision (Decision 5)

rank: Plant Head 1 · Plant QA Head 2 · PDC Head 3 · CQA Head 4 · Operations Head 5

on every new decision, override, or timer tick:
  decided   = latest decision of each authority (earlier ones kept, never edited)
  if Ops Head selected and undecided 24 calendar hours after receipt → mark TIMED_OUT, add CQA Head if not selected   (Rule 3)
  top       = highest-ranked authority that has decided, ignoring TIMED_OUT
  if top is CQA and PDC is selected and PDC has not decided → effective = PENDING_PDC_RECORD    (Rule 2)
  else effective = top.decision                         (provisional, shown to IQC Head)
  route is COMPLETE when the highest-ranked selected (not timed-out) authority has decided
     → remaining lower authorities are marked NOT_REQUIRED
     → effective decision goes to IQC Head (approve / reject) or back to the department initiator (change type)
  override by Ops/CQA (Rule 4) or Admin → appended as OVERRIDE and becomes effective

Example: Plant Head approves at 10:00, CQA rejects at 14:00, PDC (also selected) records approve at 16:00. From 16:00 the effective decision is "reject" (CQA outranks, PDC's decision is on record). All three decisions stay visible in the audit trail. Confirmed in round 2: the escalation ends when the highest-ranked selected authority decides.

Offline tablet inspection and sync (Decisions 11–12)

  • Device trust: Admin registers each Android tablet (device ID, plant) and it receives a device key kept in the Android Keystore. The inspector signs in online on that tablet once; after that a PIN unlocks the app offline, with no time limit. At every sync the server re-checks the user and device: if either was deactivated meanwhile, the data is still received but held for the Incharge to accept.
  • Check-out: the inspector downloads the lots they will inspect. Each is soft-locked to that device so two tablets cannot inspect the same lot. Locks do not expire (offline has no limit); the Incharge sees locks older than a set number of days and can release one (e.g. a lost tablet).
  • Photos offline: visual-cell photos are taken with the tablet camera through the file input, compressed on the device (e.g. max 1600 px, JPEG), kept in on-device storage and uploaded to S3 by presigned URL during sync, before the submit operation is applied.
  • No numbers generated offline: IMIR numbers are created on the server when the SAP lot arrives, before check-out.
  • Idempotent sync: every queued operation carries a client UUID; replays are ignored. Client and server timestamps are both stored for audit.
  • Server is authoritative: OK/NOK is recomputed on the server with the same shared module the tablet uses; any mismatch is logged.
  • Storage safety: data lives in SQLite inside the app, which Android does not clear to free space; local data is removed only after a successful sync; unsynced data is never discarded silently, and logout is blocked while anything is unsynced.

08PostgreSQL database design approach

Organisation

  • Schemas by concern: core (users, roles, plants, permissions), mst (masters), qms (formats, IMIR, deviation, DN), intg (SAP staging), audit.
  • uuid primary keys (gen_random_uuid()) for documents exposed in URLs; smallint/int identity keys for small lookups.
  • Human document numbers (imir_no, dn_no) are separate unique columns.
  • timestamptz everywhere, stored UTC, displayed IST.
  • numeric(12,3) for measurements (the 3-decimal rule), numeric(14,3) for quantities — never float.

Types and constraints

  • Workflow states as PostgreSQL ENUMs (tied to code, only ever appended). Business-configurable lists (deviation types, defect categories, instruments) as lookup tables.
  • CHECK constraints: lsl <= usl, quantities ≥ 0, accepted + rejected <= inward, remark required when action is escalate/hold (in service and DB).
  • Partial unique index: one APPROVED format per item; one active deviation per IMIR.
  • row_version int for optimistic locking on workflow rows.

PostgreSQL features used where they pay off

  • JSONB: raw SAP payloads, deviation-form revisions, audit before/after images, notification payloads.
  • pg_trgm GIN indexes for item code / description / vendor name search (typeahead over tens of thousands of items).
  • Partial indexes on open work: WHERE status NOT IN ('CLOSED_…') keeps inbox queries small as history grows.
  • Composite indexes matching list filters: (plant_id, status, created_at DESC).
  • Range partitioning of audit.audit_log and observations by month; BRIN on timestamps.
  • Window functions / CTEs for vendor trend and ageing reports; materialised views for vendor KPIs refreshed by the worker.

Functions, triggers, transactions

  • core.next_doc_no(doc_type, plant, period): INSERT … ON CONFLICT DO UPDATE … RETURNING on a sequence table — gap-free per plant/day, safe under concurrency.
  • Generic audit trigger writing row diffs to audit.audit_log (actor passed via SET LOCAL app.user_id).
  • updated_at trigger; business logic stays in services, not in triggers.
  • Each workflow action = one transaction: state update + history row + outbox row.
  • Least-privilege DB roles: qmas_owner (migrations), qmas_app (DML only), qmas_report (read-only for BI).
Limits are just LSL and USL (rev 2). Following Format 2, a dimensional checkpoint stores nominal, lsl, usl (numeric(12,3), either may be NULL for a one-sided limit, CHECK lsl <= usl). Auto-decision is simply lsl ≤ value ≤ usl (inclusive boundaries to be confirmed, B-11); no limit-symbol parsing at run time. Because the format structure is common (Decision 13), the 6–7k migrated formats use one import template (the "For Data" sheet layout: Item Code, Panel, Check Point, Specification, LSL, USL, UOM, Instrument). Rows still in ± notation are converted once during import, with a manual-fix report for anything unreadable (e.g. =R5).

Authentication & authorization design

  • Login: employee code + password (argon2id). Access JWT 15 min + refresh token 8–12 h (one shift), both httpOnly, Secure, SameSite=Strict cookies; refresh rotated and stored hashed so logout and admin revoke work. Lockout after 5 failed attempts.
  • Three checks per request: (1) permission — role has imir.review etc.; (2) plant scope — the record's plant is in the user's assignments for that role (visibility rules from slide 2 applied in the repository WHERE clause, not in the UI); (3) stage — the workflow engine accepts this action from this role at the current status.
  • Menu permissions keep WRL's { sectionKey: { path: bool } } contract and useRoleAccess hook, so the sidebar and route guard work the same way.
  • Segregation of duties: the creator of a format cannot approve it unless they are IQC Head (Case 2); an inspector cannot review their own IMIR.
